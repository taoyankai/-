# 数据库脚本说明

## 两类初始化脚本

| 文件 | 内容 | 使用范围 |
| --- | --- | --- |
| `init-production.sql` | 与原脚本一致的 12 张表及 7 条承运商基础数据（含韵达）；无删表语句 | 正式环境的全新空数据库，统一 Compose 默认挂载此文件 |
| `init.sql` | 建表前删表，写入演示人员、套餐、公告、订单和轨迹 | 隔离演示数据库，原文件保留不改 |

正式脚本不预置人员、套餐、库存、公告、订单、轨迹或后台账号。应用启动时由 `DataInitializer` 补齐缺失的 `admin`、`operator`、`viewer` 账号，初始密码来自 `ADMIN_INIT_PASSWORD`，已有账号密码不会因此重置。

首次登录后台并修改密码后，录入正式套餐和公告，通过 Excel 导入正式人员名单，再开放领取。

## 已建表空业务库补充演示数据

`seed-demo.sql` 用于已完成正式建表、但业务表仍为空的数据库；不替换上述首次初始化入口，不自动随容器启动执行。

- 写入 4 个套餐、13 条套餐明细、37 条人员、3 条公告、12 笔订单及 23 条配送轨迹。
- 套餐、人员、公告标注“【演示】”，订单、工号和运单使用 `DEMO` 前缀；不会创建真实物流运单。
- 人员号码是 `00000000001` 等不可收码占位值，全部设为停用，仅供后台展示；真实短信登录仍需单独录入有效真实号码。
- 保留已有后台账号、密码、承运商和审计日志。任何套餐、明细、名单、订单、轨迹、公告、地址、导入批次或 SLA 预警记录存在时，脚本会拒绝执行，不能覆盖已有业务。
- 所有业务写入在一个事务内，包含数量与关联校验；人员和订单 ID 显式指定，不依赖自增序列从 1 开始。重复导入会报错退出，不会重复增加数据。

执行前先备份数据库并暂停后端写入，使用 MySQL 8.0 客户端批量执行；**不要使用 `--force`**。若约束检查失败，应让客户端退出、连接断开，使事务回滚，不要继续提交。执行后核对数量与关联并恢复后端。普通重启和版本更新不需要重新导入。

这批订单用于展示待发货、运输、签收及临近/超过发货时限等状态，会计入后台统计和 SLA 扫描。当前通知通道为 mock；以后接入真实告警短信或真实物流前，应先清理演示业务并核对正式数据。不要对演示订单安排真实发货。

正式启用前另行备份和核对演示数据的处理范围，不运行 `init.sql` 清库，也不删除数据卷。

本次服务器导入数量、备份位置和验收结果见[服务器演示数据初始化记录](../docs/服务器演示数据初始化记录-20261023.md)。

## 执行时机

MySQL 镜像只会在数据目录为空、首次初始化时执行 `/docker-entrypoint-initdb.d/` 下的脚本。Compose 将 `init-production.sql` 只读挂载为 `01-init.sql`，命名卷 `hz-mysql-data` 保存数据库。

- 普通容器重建、代码更新、服务重启不重新初始化数据库。
- 修改初始化脚本不会修改已有数据库，也不会自动清除已有演示记录。
- 正式脚本用普通 `CREATE TABLE`，已有同名表会报错；它不是可重复导入的升级脚本。
- 不把原演示脚本导入业务库，不通过删除数据卷实现更新。

## 已有数据库与后续迁移

已有数据库继续使用原数据卷。上线前先确认其中是否仍有演示数据；清理或迁移需单独制定方案、备份并核对，不能靠切换初始化文件完成。

后续表结构变更应提供独立、带版本号的迁移 SQL，记录适用版本、执行顺序及恢复方法；本次未引入迁移框架，也未向任何数据库执行 SQL。应用当前已有的启动兼容逻辑继续由源码维护，不能代替今后的迁移方案。

若初始化中断，先查看 MySQL 日志及已创建的表，再决定恢复办法；已有数据时不要直接重新导入或删除卷。

备份方法见[部署手册](../deploy/server/README.md#数据库备份)。
