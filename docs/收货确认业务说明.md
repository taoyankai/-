# 收货确认

## 完成规则

平台签收、用户确认收货、后台代确认收货，任一种完成后订单统一为“已签收”（40）。不新增独立的实际收货状态，不要求其他角色再次确认，不新增数据库字段。

用户和后台仅可确认“已发货”（10）、“运输中”（20）、“派送中”（30）且已绑定运单、存在发货时间的订单。待发货、已取消、配送异常、已退回订单不可人工确认。已签收订单再次提交时返回原签收信息，不覆盖时间、不追加确认轨迹。

## 页面入口

- 后台：物流跟踪列表、物流轨迹窗口、订单详情中的“代确认收货”。管理员和运营人员可操作，只读账号不显示按钮且接口拒绝写入。弹窗提供选填备注，最多200字；确认方式、操作人和备注写入轨迹，同时记录后台操作日志。
- 微信小程序：订单详情中的“确认收货”。二次确认实际收到商品后提交，仅允许操作本人订单。取消弹窗不发送请求。
- 网页用户端：订单详情同样提供“确认收货”，采用相同规则。
- 已签收后隐藏确认按钮，详情展示签收时间。后台备注随确认轨迹显示在用户订单详情中。

## 接口

- `POST /api/admin/orders/{id}/confirm-receipt`：后台代确认，JSON体可省略，也可提交 `{"remark":"选填备注"}`。
- `POST /api/client/orders/{id}/confirm-receipt`：用户确认，身份取自登录凭证，不接受前端指定操作人。
- 旧 `POST /api/admin/orders/{id}/push-status` 仅保留代确认收货兼容路径：`status` 必须为40，`description` 为选填备注；其他目标状态拒绝，不开放人工推进其他状态。
- 成功响应包含 `orderId`、`orderNo`、`status`、`signTime`、`changed`。`changed=false` 表示此前已经签收，本次未重复修改。

## 并发与数据

确认操作以订单行锁串行处理，在一个事务内更新签收状态和写入轨迹。多个请求只有首次确认写入成功；写轨迹失败会回滚状态和时间。

承运商同步改为按原状态、承运商和运单号进行条件更新，只更新状态、签收时间及更新时间。查询期间发生人工确认时，旧查询不能覆盖已经完成的签收，也不会覆盖其他订单字段。首次签收时间保留。

物流同步仍共用原30分钟限频；确认收货不调用快递100、不受物流查询限频影响。已签收后沿用原逻辑停止物流同步。
