## 1. SSH：分开判断网络、主机身份和登录授权

初次连接先受到本机执行环境的网络权限限制。放行指定服务器连接后，服务器返回：

```text
Permission denied (publickey,password)
```

此时已经收到服务器认证响应，需继续检查登录授权。后续通过交互式终端使用密码登录，备份服务器原有 `authorized_keys` 后追加项目专用公钥，并验证新的非交互登录成功。GitHub 使用的本机私钥与服务器连接专用私钥分别保留在本机，没有将私钥复制到服务器或仓库。

第一次打开的密码窗口未在用户桌面显示，原因没有确认，记录为“交互窗口未显示”；后续改用交互终端解决，没有据此修改服务器 SSH 配置或重置密码。

`ssh-keyscan` 能返回公钥只证明 SSH 入口有响应。信任主机前仍需核对指纹；本次 GitHub SSH 443 指纹已与 GitHub 官方 HTTPS 元数据核对一致。不要把连接超时直接归因为密钥错误，也不要关闭主机验证来绕过问题。

## 2. Docker 安装与镜像下载

最初服务器未安装 Docker，官方下载入口还出现 `curl: (35) ... Connection reset by peer`。实际改用 Ubuntu 软件仓库安装 `docker.io`、`docker-compose-v2`，不依赖失败的安装入口。

后续构建检查发现 `docker buildx` 不存在，再从同一系统仓库安装 `docker-buildx`，验证版本命令成功。Docker 能运行、Compose 能解析，不代表构建插件也已安装。

Docker Hub 直连曾报连接超时。腾讯云地址 `https://mirror.ccs.tencentyun.com/v2/` 返回 HTTP 200 后，先检查原有 `/etc/docker/daemon.json`，保留其他配置并设置 `registry-mirrors`。配置先通过 `dockerd --validate`，确认当时没有运行容器后重启 Docker。

之后实际拉取以下镜像全部成功，才确认镜像下载链路可用：

- `nginx:1.27-alpine`
- `redis:7.4-alpine`
- `mysql:8.0`
- `maven:3.9-eclipse-temurin-17`
- `eclipse-temurin:17-jre-alpine`

镜像加速只处理相应 Docker 镜像请求；GitHub、Maven、Alpine 软件包需要分别检查。Registry 根地址返回200，不能代替具体镜像下载验证。

## 3. GitHub 旧版本与本机网络超时

发布前，本地改造还没有提交到 GitHub。远端默认分支已合并此前业务变更，其基线代码树与本地原分支相同，只多出合并记录。取得最新远端历史后，先快进本地基线，再提交这次改造，保留已有合并历史。

本机直连 GitHub HTTPS 和 SSH 443 都曾超时；服务器则通过 HTTPS、HTTP/1.1 实际读取 HEAD 并克隆成功。因此本次采用：

- 本地上传：使用自己的 Ubuntu 服务器作为 SSH 跳板，验证 GitHub 返回身份认证成功后正常推送；私钥留在本机，不修改全局 SSH 配置。
- 服务器下载：仓库使用 HTTPS，仓库内设置 `http.version=HTTP/1.1`。公开仓库拉取不需要再配置 GitHub 部署密钥。
- 版本一致：默认分支、开发分支与新标签原子推送；服务器部署标签对应的提交，成功后写入 `current-release`。

本次没有证明早先 HTTPS 超时的唯一底层原因；可确认的是复测和实际克隆成功。后续仍应以当前网络实测为准。每次代码修复创建新标签，不覆盖旧标签，不强推已有历史。

## 4. Alpine 系统包下载拖慢构建

首轮 Java 编译成功，但运行镜像中的 `apk add --no-cache tzdata curl` 长期没有完成；该步骤最终耗时约341秒。独立诊断结果为：

| 检查 | 实际结果 |
| --- | --- |
| 宿主机下载官方索引 | 成功 |
| 容器中 BusyBox wget 下载官方索引 | 成功 |
| 容器中 apk 使用官方源安装 | 出现 TLS 错误，超过45秒诊断限制 |
| 同一基础镜像中 apk 使用阿里云源安装 | 成功 |

因此不能用宿主机联网或另一种下载工具成功，替代实际构建命令验证。`server/Dockerfile` 增加可配置的 `ALPINE_MIRROR`，默认 `https://mirrors.aliyun.com/alpine`，并设置 `apk --timeout 20`。2GB Compose 覆盖传入同名构建参数。

`v1.0.1` 在服务器实际重建时，该安装步骤约6秒完成。APK 超时设置不代表整个 Docker 构建最多20秒。

## 5. 源码解包权限导致初始化失败

这是本次首轮启动失败的直接原因。部署脚本为了保护私密配置、备份和版本文件设置了 `umask 077`，同一设置也影响了 Git 源码解包：SQL 和页面文件成为600，目录成为700。

MySQL 镜像以非root用户读取初始化脚本时失败：

```text
/docker-entrypoint-initdb.d/01-init.sql: Permission denied
Table 'hz_delivery.t_admin' doesn't exist
```

MySQL 数据目录和数据库已创建，但业务表未建立；后端初始化因此失败并反复重启，Nginx等待后端健康。该权限设置也会影响 Nginx 非root worker 读取静态页面。

修复位于 `deploy/server/deploy-version.sh`，仅在源码解包子进程使用022，并明确不恢复归档所有者与原权限：

```bash
(
    umask 022
    git -C "$repo_root" archive "$commit" |
        tar --no-same-owner --no-same-permissions -x -C "$release_dir"
)
```

服务器实测权限如下：

| 对象 | 修复后的权限 |
| --- | --- |
| 初始化 SQL、HTML 文件 | 644 |
| 挂载的 `admin/`、`miniapp/` 目录 | 755 |
| release 根目录 | 700；挂载子目录可读，无需放宽整个发布目录 |
| 生产 `server.env`、版本记录、数据库备份 | 600 |

本次恢复先核对容器属于 `hz-delivery`，停止反复失败的API，并确认目标数据库表数为0。随后备份空库，使用当前正式初始化脚本补做建表，确认12张表，再部署修复版。没有删除数据卷，没有导入演示数据。

此恢复过程仅适用于已确认的空库。已有表、部分初始化或已有业务数据时，应先检查结构和备份，再制定对应修复；不能直接重跑完整初始化 SQL。MySQL 数据目录一旦初始化，单纯重启容器不会重新执行首次初始化脚本。

## 6. 健康检查与密码日志

原 MySQL 健康检查只判断进程响应，空库无业务表时仍可能显示健康。现改为认证连接指定数据库，并查询 `t_admin`、`t_order`、`t_carrier`，关键表不存在时不放行后端启动。

本次还移除了 `DataInitializer.java` 输出初始后台密码的日志。初始密码由独立配置提供，文档和验证报告只记录字段名及配置位置，不记录值。

生产配置通过加密 SSH 单独迁移到 `~/.config/hz-delivery/server.env`，权限600；不与源码一起上传 GitHub。本次操作工具曾因缺少针对具体密钥载荷的授权拒绝传输，用户明确批准后才完成，这属于操作授权检查。

## 7. 公网访问与 SSH 隧道

本次 `compose.2gb.yml` 将 Nginx 绑定到服务器 `127.0.0.1:80`。因此公网 IP 不能直接打开业务页面，需通过 SSH 隧道访问；本机 `127.0.0.1:18082` 对应服务器入口。

在本机 PowerShell 运行并保持连接：

```powershell
ssh -N -L 18082:127.0.0.1:80 -i "$env:USERPROFILE\.ssh\hz_delivery_118_89_27_5_ed25519" ubuntu@118.89.27.5
```

已有18082隧道时无需重复启动。此命令的密钥路径对应本次电脑；更换电脑需配置自己的授权密钥。

- H5：`http://127.0.0.1:18082/`
- 后台：`http://127.0.0.1:18082/admin/`
- 健康：`http://127.0.0.1:18082/actuator/health`

公网 HTTPS、正式开放入口和微信端发布尚未在本次完成。页面能打开不等于已经开放公网。
