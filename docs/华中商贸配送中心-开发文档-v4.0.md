## 0. 本次交付说明（v3.0 → v4.0 的变化）

v3.0 是一份业务方案设计稿，产出物只有两个演示用 HTML 页面（数据写死在页面里）。v4.0 把它补齐为一个**可部署、可联调、可验收**的完整系统。

| 维度 | v3.0（设计稿 + 前端演示） | v4.0（本次交付） |
| --- | --- | --- |
| 后端服务 | ❌ 无 | ✅ Spring Boot 3.2 服务，8 个控制器 / 70+ 接口 |
| 数据库 | ❌ 无 | ✅ MySQL 8.0，10 张表 + 初始化脚本 |
| 缓存 | ❌ 无 | ✅ Redis 7（登录态、验证码、订单号序列） |
| 部署 | ❌ 只能双击打开 HTML | ✅ Docker Compose 四容器一键启动，可原样上云 |
| 前端数据 | 页面内写死的 mock 数组 | 全部改为真实 HTTP 调用，含登录态与下载/上传 |
| 名单来源 | 页面内生成的假名单 | 甲方 Excel 导入（模板下载 → 校验 → 批次留痕 → 可筛选导出） |
| 领取规则 | 未约束 | 每人限领 1 份，服务端原子扣减 |
| 权限 | 无 | admin / operator / viewer 三角色，只读角色后端强制拦截 |
| 验证 | 手工点 | 全量回归 390 项断言全绿（**小程序原生端静态 19 + 小程序端接口契约 44** + 后端 85 + 后台 86 + C 端 84 + 回退 6 + 承运商与物流 17 + 改址与审计与预警 33 + 登录防爆破 16），另有真实短信联调 15 项；端到端截图核查 |

## 3. 数据库设计

库名 `hz_delivery`，字符集 `utf8mb4`。脚本 `db/init.sql` 使用 `DROP TABLE IF EXISTS` + `CREATE TABLE`，**可重复执行以复位演示数据**。

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `t_admin` | 后台账号 | `username`、`password`（PBKDF2）、`role`(admin/operator/viewer)、`status` |
| `t_grantee` | 教职工名单（甲方 Excel 导入） | `emp_no`、`name`、`phone`（唯一）、`org`、`dept`、`quota`、`used`、`status`、`batch_id` |
| `t_package` | 慰问品套餐 | `no`、`name`、`sub`、`price`、`stock`、`warn`、`sort`、`status`、`change_reason` |
| `t_package_item` | 套餐内容清单 | `package_id`、`name`、`spec`、`qty`、`unit`、`sort` |
| `t_order` | 领取订单 | `order_no`（唯一）、`grantee_id`、`package_id`、`goods_snapshot`、`status`、`sla_deadline`、`carrier`、`waybill_no`、**`expect_carrier`（用户期望承运商编码）**、**`expect_carrier_name`（名称快照）**、**`addr_change_count`（改址次数，限 1 次）**、`exception_reason` |
| `t_order_track` | 物流轨迹 | `order_id`、`order_no`、`status`、`description`、`track_time`、`source` |
| `t_address` | 收货地址簿 | `grantee_id`、`receiver`、`phone`、省市区、`detail`、`allow_station`、`is_default` |
| `t_notice` | 公告与说明 | `type`(1 首页公告 / 2 配送说明 / 3 偏远地区说明)、`title`、`content`、`status`、`sort` |
| `t_import_batch` | 导入批次留痕 | `batch_no`、`type`、`file_name`、`total_count`、`success_count`、`fail_count`、`fail_detail`、`operator` |
| `t_carrier` | 承运商字典 | `code`、`name`、`track_url`、`phone`、`status` |
| **`t_operation_log`** | **操作审计日志（个人信息合规）** | `admin_id`、`admin_account`、`admin_name`、`admin_role`、`module`、`action`、`target`、`detail`、`row_count`、`ip`、`user_agent`、`result` |

## 4. 后端工程实现

### 4.1 分层职责

```
Controller  → 只做参数绑定与响应包装，不写业务
Service     → 业务规则、事务边界、并发控制
Mapper      → 数据访问（含原子 UPDATE 语句）
common      → 统一响应、错误码、异常处理、工具
```

统一响应体：

```json
{ "code": 0, "msg": "ok", "data": {...}, "timestamp": 1789442925460 }
```

`code === 0` 表示成功，其余为业务错误码。分页数据统一为 `{ list, total, page, size }`。

### 4.2 鉴权与权限模型

| 项 | 说明 |
| --- | --- |
| 凭证 | 登录成功后下发 token，客户端以 `X-Token` 请求头携带 |
| 存储 | Redis：`hz:token:client:{token}` → 教职工 ID；`hz:token:admin:{token}` → 管理员 ID |
| 有效期 | 后台 token 43200 秒（12 小时）；验证码 300 秒 |
| 拦截 | `AuthInterceptor` 拦截 `/api/client/**` 与 `/api/admin/**`，放行 `/api/client/auth/**`、`/api/admin/auth/login` |
| 失败响应 | **HTTP 200 + `code: 401`**（前端据此清除本地登录态并弹回登录页） |

**角色与权限**

| 角色 | 权限 | 落地方式 |
| --- | --- | --- |
| `admin` 系统管理员 | 全部功能 | — |
| `operator` 项目运营 | 全部业务操作 | — |
| `viewer` 只读查看 | **仅查询与导出** | `AuthInterceptor` 对非 GET 请求查库校验角色，命中 viewer 直接返回 `403 当前为只读账号，无操作权限`；前端同时拦截写操作并显示只读提示条 |

### 4.4 关键业务实现

**① 每人只能选择一个套餐**

- 名单导入时 `quota` 取配置 `hz.delivery.default-quota`，本项目固定为 1。
- 下单时以原子 SQL 扣减，避免并发超领：

  ```sql
  UPDATE t_grantee SET used = used + 1 WHERE id = ? AND used < quota
  ```

  影响行数为 0 即表示额度已用尽，返回 `1103`。
- 因此同一教职工重复提交会被拦截，且**不会**产生第二笔订单。

**② 收到配送信息后 10 日内发货（SLA）**

- 下单成功即写入 `sla_deadline = now + hz.delivery.sla-days(10) 天`。
- `SlaUtil.remainDays` 对正数取**向上取整**（剩余 3 小时显示为 1 天，而非 0 天）。
- 预警分级：剩余 > 3 天 = 安全；≤ 3 天 = 预警；≤ 1 天 = 紧急；已过期 = 超时。
- 看板与 SLA 页实时展示四档分布；超时订单可登记原因，写入 `exception_reason` 并补一条轨迹，作为履约说明材料。
- **主动预警（定时任务）**：`SlaAlertJob` 每日 `SLA_ALERT_CRON`（默认 09:30）自动扫描待发货订单，
  按「已超期 / 24 小时内 / 72 小时内」三档生成告警记录到 `t_sla_alert`；
  当出现超期或 24 小时内到期的订单时，通过短信通道 `sendText` 通知库管（接收号码 `SLA_ALERT_PHONE`，
  留空则只落库不发短信）。同日重复扫描幂等、不产生重复记录；
  后台 SLA 页可「立即扫描预警」手动触发（默认不发短信），也可回看最近 14 天预警记录。

**③ 送货上门、默认不放代收点**

- C 端 `validateAddress` 做前置校验：详细地址需 ≥ 8 字、含数字门牌、含「室 / 栋 / 幢 / 号楼 / 单元 / 号 / 巷 / 组 / 村 / 大厦 / 公寓 / 小区 / 组团 / 座」之一。
- 服务端 `AddressValidator` 做**最终兜底**（前端可绕过，服务端不可）。
- `allow_station` 默认 `false`（配置 `allow-station-default: false`），发货时随承运商信息一并透传。

**④ 库存与超卖**

- 下单原子扣减：`UPDATE t_package SET stock = stock - ? WHERE id = ? AND stock >= ?`。
- 取消订单回补库存并释放领取额度，两件事在同一事务内完成。

**⑤ 重复提交幂等**

下单顺序为：**① 参数与地址校验 → ② 幂等检查（该教职工是否已有未取消订单）→ ③ 额度扣减 → ④ 库存扣减 → ⑤ 落单**。

幂等检查必须早于额度扣减，否则重复提交会返回「已领取过」而非「请勿重复提交」（错误码 1304），语义不准确。此顺序为联调阶段实测修正项。

**⑥ 套餐内容快照**

招标要求「不允许私自更改方案内容」。下单时把套餐内容序列化为 JSON 存入 `t_order.goods_snapshot`，后台后续修改套餐不影响历史订单展示。

**⑦ 订单状态机**

```
0 待发货 ──发货──► 10 已发货 ──► 20 运输中 ──► 30 派送中 ──► 40 已签收
   │                                                      └─► 60 配送异常
   └──取消──► 50 已取消                                     └─► 70 已退回
```

发货使用条件更新（`WHERE status = 0 AND waybill_no IS NULL`），防止并发重复发货；仅「已发货」状态允许撤回修正。

**⑧ 收货地址自助修改（未发货前，限 1 次）**

- 规则与招标「送货上门、不得擅投代收点」配套：**发货后地址已随运单下发承运商，自行改派会造成丢件**，
  故仅「待发货」可改，且每单只能自助改 1 次，超出后提示联系客服。
- `t_order.addr_change_count` 记录修改次数；条件更新带 `status` 与次数双重条件，并发下只有一次生效。
- 修改地址**写入物流轨迹**（何时改、改成什么），发货前可核对、发货后可追溯；地址内容不完整沿用 `AddressValidator` 校验。
- 前端：待发货订单显示「修改地址」，已用过 1 次后按钮消失、改为客服引导；发货后彻底锁定（返回 1306）。

**⑨ 导出操作审计（个人信息合规）**

- 名单与订单导出含教职工姓名、手机号与住址，属个人信息，导出必须留痕。
- 新增 `t_operation_log`，记录**操作人（账号 / 姓名 / 角色）、时间、客户端 IP、浏览器标识、
  模块、动作、筛选条件、导出条数、结果**；名单导入、订单导出、待发货清单导出均已埋点。
- 客户端 IP 取自 `X-Forwarded-For` 首段（nginx 用 `$proxy_add_x_forwarded_for` 保留客户端真实地址）。
- 后台新增「操作日志」页，支持按模块 / 动作 / 操作人 / 日期筛选，供个人信息保护审计追溯。

### 4.5 短信通道与 C 端登录方式（均为配置项，可切换）

**背景**：项目早期未采购短信服务，验证码"发不出去"、C 端无法登录，因此先做了"手机号 + 姓名"核验过渡。
现已接入**河北大学统一短信服务平台**，真实短信可下发；同时把"登录方式"本身也做成配置项，
两种方式共用同一套名单校验与防爆破逻辑。

#### 4.5.1 登录方式开关（`LOGIN_MODE`）

| 取值 | 登录要素 | 适用场景 |
| --- | --- | --- |
| `sms`（当前默认） | 手机号 + **短信验证码** | 正式使用；要求名单内手机号均为可收短信的真实号码 |
| `name` | 手机号 + **姓名**（须与甲方名单登记一致） | **仅演示环境**。姓名属公开信息，拿到同事手机号即可冒领，勿在生产使用 |

- C 端登录页**不写死登录方式**：启动时调 `GET /api/client/auth/mode`，按返回的 `mode` 决定渲染
  「姓名」输入框还是「短信验证码 + 获取验证码」按钮，因此**切换只改后端配置，前端零改动**。
- `name` 方式下调用 `send-code` 返回 **1007**（当前登录方式无需短信验证码），
  避免前端把"不需要发"误判成"发送失败"。

**防爆破（`name` 方式必须开启）**：姓名取值空间很小，若不限次，拿到同事手机号即可枚举姓名冒领。为此统一加了三层防护：

| 层 | 行为 |
| --- | --- |
| 计数 | 同一手机号连续核验失败，逐次提示「还可尝试 N 次」 |
| 锁定 | 达到 `LOGIN_MAX_FAIL`（默认 5）次 → 临时锁定 `LOGIN_LOCK_MINUTES`（默认 10）分钟，返回 **1006** |
| 锁定期 | 锁定期间**连名单都不查、姓名正确也一律拒绝**，避免被当成"名单探测器" |

失败计数与锁定都放在 Redis，登录成功即清零，不会把合法用户永久挡住。
`LOGIN_MODE=sms` 时同样受此限制（防脚本爆破 6 位验证码）。

**发送量闸门（防短信轰炸）**：60 秒频控只能拦「同一号码连点」，拦不住「拿着名单逐个号码轰炸」——
后者既消耗短信费用又骚扰教职工。因此再加一道**每日总量**闸门：同一手机号每日最多发送
`SMS_DAILY_LIMIT`（默认 10）条，超限返回 1004；**发送失败会退还当日额度**，避免通道抖动把用户当天配额耗光。

**接口最小化**：`GET /api/client/auth/check` 免登录可调，原先会回传脱敏姓名 / 单位 / 部门，
等同于把花名册开放给任何知道手机号的人（脱敏成「张*」后结合单位信息同样可推断）。
现已收敛为**只回「是否在名单」**，不再回传任何个人信息；登录页也不再依赖它。

```bash
LOGIN_MODE=sms           # 手机号 + 短信验证码（当前默认）
LOGIN_MODE=name          # 手机号 + 姓名（仅演示环境）
LOGIN_MAX_FAIL=5         # 连续核验失败上限，达到即临时锁定
LOGIN_LOCK_MINUTES=10    # 锁定时长（分钟），同时作为失败计数窗口
SMS_DAILY_LIMIT=10       # 同一手机号每日验证码发送上限
```

#### 4.5.2 短信通道（可插拔，现已接入真实通道）

```
service/sms/
├── SmsSender.java        接口：provider() / sendCode(phone, code) / sendText(phone, text)
├── MockSmsSender.java    演示通道：仅写日志，验证码回传前端便于联调
├── HbuSmsSender.java     河北大学统一短信服务平台（真实发送，已按接口文档接入）
└── AliyunSmsSender.java  占位骨架：未补全 SDK 时抛明确异常，避免"看似发了实际没发"
```

**河北大学平台对接要点**（`SMS_PROVIDER=hbu`）

| 项 | 内容 |
| --- | --- |
| 接口地址 | `POST http://sim.hbu.edu.cn/sms-hbu/api`（`application/x-www-form-urlencoded; charset=UTF-8`） |
| 请求参数 | `cid`（客户端 ID，当前 7）、`key`（密钥）、`code`（手机号），以及 **`model` + `variables`（模板发送）** 或 `msg`（自定义正文）**二选一** |
| 验证码模板 | `model=yzmmb`，变量 `{"code":"123456","time":"5"}`（`time` 为验证码有效期分钟数） |
| 返回值 | 成功返回 `ok`，失败返回具体错误信息；本实现把原文带进异常提示，便于直接定位 |
| 平台约束 | 短信签名由平台自动添加；单条正文上限 60 字；`msg` 与 `model` 不能同时传 |

**安全设计**

- 密钥**不写进代码**，通过 `SMS_HBU_KEY` 环境变量注入；
- 一旦 `SMS_PROVIDER≠mock`，代码**强制忽略** `MOCK_SMS_CODE`、验证码改为随机 6 位，并在启动时打 WARN
  —— 杜绝"真实短信 + 固定验证码"并存导致的越权登录；
- 真实通道下 `send-code` 响应**不回传**验证码（只回 `sent` / `ttl` / `provider`）；
- 发送失败会**同时撤掉验证码与频控键**，用户可立即重试，而不是干等 60 秒；
- 短信正文超过字数上限、密钥未配置、平台不可达，都会抛出带原因的明确异常（1009），不会静默失败。

#### 4.5.3 后台短信通道自检

部署到服务器后，"短信到底发得出去吗"不必靠造业务数据来试：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/sms/status` | 返回当前通道、自检开关、登录方式 |
| POST | `/api/admin/sms/test?phone=` | 真实发一条测试短信，并原样返回平台响应 |

该接口位于 `/api/admin/**` 之下（需管理员登录态），并由 `SMS_TEST_ENABLED` 二次控制，**默认关闭**；
排查时临时打开、用完关闭。

#### 4.5.4 上线前必做

1. `.env` 设 `SMS_PROVIDER=hbu` 并填入 `SMS_HBU_KEY`；
2. 确认 `LOGIN_MODE`（用短信登录则设 `sms`，且名单内手机号须为真实可收短信的号码）；
3. `SMS_TEST_ENABLED=false`，`MOCK_SMS_CODE` 一并清空避免混淆；
4. 关闭 C 端登录页演示提示（`miniapp/index.html` 中 `SHOW_DEMO_HINT = false`），避免演示手机号与姓名出现在正式环境；
5. 用后台「短信通道自检」发一条真实短信，确认通道可用。

> 生产建议：加图形验证码 / 滑块前置。
> 当前已实现：60 秒发送频控 + 每日发送上限（1004）、失败计数与临时锁定（1006）、
> 验证码 5 分钟有效且**一次性使用**（登录成功即作废，同码重放返回 1003）。

### 4.6 用户自选合作物流

**数据模型**：`t_order` 增加两列，下单时快照用户选择。

```sql
`expect_carrier`      VARCHAR(20)  COMMENT '用户期望承运商编码（SF/JD/YTO/ZTO/EMS）',
`expect_carrier_name` VARCHAR(50)  COMMENT '用户期望承运商名称（快照，便于展示）'
```

**接口**：`GET /api/client/carriers` → 仅返回 `status = 1` 的承运商，C 端渲染为单选卡片。

**校验规则**（`OrderService.create`）

| 传参 | 行为 |
| --- | --- |
| `carrierCode` 合法且已启用 | 落库 `expect_carrier` + 名称快照 |
| `carrierCode` 不存在 / 已停用 | 拒绝下单，返回参数错误，提示重新选择 |
| 不传 `carrierCode` | 默认取启用列表第一家（顺丰），保证向后兼容 |

**后台协同**：发货弹窗的承运商下拉**默认选中用户期望的承运商**，操作员可改（如目的地超出该快递覆盖范围），
但默认值降低了改单率；订单详情同时展示"期望承运商"与实际承运商，便于核对履约偏差。

> 说明：**包邮**为全站固定策略，用户自选物流**不影响运费**（均为 0），仅影响履约路径与时效体验。
> 偏远地区（新疆 / 西藏 / 内蒙古部分 / 青海 / 甘肃部分）在 C 端单独公示时效。

### 4.7 C 端物流进度查询

**接口**：`GET /api/client/orders/track?waybillNo=<运单号>`，需登录态。

**权限与异常**（关键：不得越权查看他人包裹）

| 场景 | 返回 |
| --- | --- |
| 运单号为空 | 400，提示"请填写运单号" |
| 运单号不存在 | **1301** 未查询到该运单号对应的订单，请核对后重试 |
| 运单号属于他人订单 | **1303** 该运单号不属于您的订单 |
| 本人订单 | 200，返回订单详情 + `traces[]` 轨迹节点 + 承运商 + 收货地址 |

**前端页面**（`miniapp` 的 `pageTrack()`）

- 运单号输入框 + 查询按钮（含 loading 与错误提示）；
- 查询结果卡片：承运商、运单号、收货地址、轨迹时间轴；
- **尚未产生轨迹时**给出友好文案："商家已发货，正在等待承运商揽收，稍后将有轨迹更新"；
- 下方列出"我的运单"（状态 ≥ 已发货的订单），一键带入运单号，避免用户手抄长串单号。

> **实现要点：轨迹按需拉取**
> 订单**列表**接口不返回轨迹明细（`traces` 为 `null`），只有**详情**接口返回。
> 因此详情页渲染后调用 `ensureTraces(orderId)` 拉一次详情并回填 `o.traces`，然后重渲染。
> 该方法用 `Map` 做 in-flight 去重——同一订单在请求返回前不会重复发起，返回后 `traces` 非空即不再请求。
> 拉取失败时静默降级为"暂无轨迹"，不阻塞页面。

### 4.8 前端接口地址自动回退（C 端登录失败的根因修复）

**现象**：在静态预览面板中打开前端页面时，能渲染界面但登录一直失败。

**根因**：预览面板以静态文件方式托管页面，其源（如 `http://127.0.0.1:10394`）**不提供 `/api` 反向代理**，
而前端原本写死同源 `/api`，请求直接 404。

**方案**：接口适配层改为**候选地址列表 + 失败自动切换 + 成功记忆**。

```js
const API_CANDIDATES = [ location.origin + '/api', 'http://localhost/api' ];
let apiBase = null;                        // 首次请求时按序探测
// 探测规则：候选返回 404 / 非 JSON（HTML 错误页）→ 判定该源不可用，切下一个
//           业务错误（如 1004 验证码过于频繁）→ 说明接口通了，不回退，直接抛给业务层
// 命中后写入 apiBase，后续所有请求直接复用，不再重复探测
```

**要点**

- **只在"接口不可达"时回退**，业务错误绝不回退——否则会把"验证码太频繁"误判为"换了服务器"，导致状态漂移；
- 探测成功即记忆，避免每次请求都先撞一次 404；
- C 端与后台前端使用同一套适配逻辑，行为一致。

## 7. 前端接入说明

两个页面均为**单文件 HTML**（HTML + CSS + JS 内联），零构建，直接由 Nginx 托管。

### 7.1 接口适配层

两个页面各有一段同构的 `API` 适配层：

- `API_CANDIDATES` / `API.base`：**候选地址列表 + 自动回退 + 命中记忆**。按序探测 `location.origin + '/api'`
  （同源部署 / Nginx 反代）→ `http://localhost/api`（本地联调 / 静态预览面板）。判定依据是
  "**接口是否可达**"（404 或返回 HTML 而非 JSON 视为不可达），业务错误码（如 1004）**不触发回退**。
  成功一次后写入 `API.base`，后续请求直接复用。详见 §4.8。
- `API.req/raw`：自动附加 `X-Token`，统一解包 `{code,msg,data}`，`code !== 0` 抛错；`code === 401` 时清 token 并弹回登录页。
- `API.upload`：`FormData` 上传 Excel。
- `API.download`：带鉴权头拉取文件流，解析 `Content-Disposition` 还原中文文件名后触发保存。**不能用 `<a href>` 直接下载，因为导出接口需要校验 token。**
- `API.restore/setToken`：登录态持久化到 `localStorage`（`hz_admin_token` / `hz_client_token`），`file://` 下 `localStorage` 不可用时降级为内存态。

### 7.2 数据归一化

后端返回 ISO-8601 时间串（`2026-09-01T11:20:04`），部分浏览器（尤其 iOS Safari）不能直接解析。两个页面统一用 `ts()` 归一化为 `yyyy/MM/dd HH:mm:ss` 后再取时间戳，并对带毫秒/时区后缀的串回落到原生解析。

> 该问题由截图核查发现：订单详情「提交时间」曾整行显示 `NaN-NaN-NaN NaN:NaN`。

后台还会把后端数据归一化为页面既有渲染结构：

- 承运商 `carrier`（编码）→ `carrierCode`，`exceptionReason` → `delayReason`
- 领取状态 `pickStatus` 由订单推导（0 未提交 / 1 已提交待发货 / 2 已发货 / 3 已签收）
- 公告 `type` 数字 → 中文（1 首页公告 / 2 配送说明 / 3 偏远地区说明）
- 组织树由名单的 `org` / `dept` 动态推导，不再写死单位列表

### 7.3 前端页面与登录

| 页面 | 登录态处理 |
| --- | --- |
| `miniapp/index.html` | 启动时用本地 token 尝试恢复会话，失败则跳登录页 |
| `admin/index.html` | 无 token 时显示登录浮层；有 token 时先校验 `/admin/auth/profile`；数据加载成功后自动关闭登录浮层 |

管理员演示账号：`admin` / `operator` / `viewer`，初始密码见 `.env` 的 `ADMIN_INIT_PASSWORD`（默认 `hz@2026`）。
C 端演示手机号：`13900139003`（未领取，可走完整领取流程）、`13800138000`（已领取，可看订单与轨迹）；演示验证码固定 `123456`。

### 8.7 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| `docker-compose` 报 `unknown command: docker compose` | 老版本只有独立二进制，改用 `docker-compose`（带连字符） |
| 拉镜像超时 / `registry-1.docker.io` 连接失败 | 配置 Docker 镜像加速；或为 Docker Desktop 设置代理（`settings-store.json` 中 `OverrideProxyHTTP/HTTPS`） |
| Maven 依赖下载失败 | `server/settings.xml` 已配置阿里云镜像；确认构建时使用了该文件 |
| 后端启动报 `UnsupportedEncodingException: utf8mb4` | JDBC URL 的 `characterEncoding` 必须写 `UTF-8`（Connector/J 会自动映射到 utf8mb4） |
| 导出 Excel 文件名乱码 | 必须按 `filename*=UTF-8''` 解析，不能用 `filename=` |
| 后台登录后立刻被弹回登录页 | 后端鉴权失败返回的是 HTTP 200 + `code:401`，前端需按业务码判断，不能只看 HTTP 状态 |
| 页面时间显示 `NaN-NaN-NaN` | 后端返回 ISO-8601（含 `T`），需先归一化分隔符再 `new Date()` |
| 小程序页面白屏且地址栏是 `/h5/xxx` | Nginx 中 C 端 H5 的根目录就是 `/`，不存在 `/h5` 前缀 |
| 经网关访问 `/actuator/health` 返回 400（Tomcat 页面） | 该 location 漏了 `proxy_set_header Host $host`，nginx 会把 `Host` 设成上游名。**上游名带下划线（如 `hz_api`）不符合主机名规范，Tomcat 直接 400**；所有 `proxy_pass` 都应显式透传 `Host` |

### 8.8 微信小程序端部署（原生页面 + 可选云函数通道）

**方案沿革**：早期采用 **web-view 壳**（小程序承载已部署的 H5，接口层零改动）。该方案在上线阶段被
**主体类型**挡下——**个人主体小程序不支持 `web-view` 组件**；即便换成企业主体，web-view 加载的域名

> 两端共用同一套后端接口，业务规则（额度、SLA、地址校验、承运商自选、改址）完全一致。

**两条请求通道（改 `config.js` 一个开关切换）**

| 通道 | `useCloud` | 适用场景 | 域名/备案要求 |
| --- | --- | --- | --- |
| `wx.request` 直连后端 | `false` | 本地联调 | 需在开发者工具勾「不校验合法域名」 |
| 云函数转发 | `true` | 正式环境 | **无需配置服务器域名、无需 ICP 备案** |

**云函数为什么能免备案**：`wx.request` 受小程序「服务器域名」白名单约束（域名须备案）；而
`wx.cloud.callFunction` 走云开发内网通道，云函数运行在腾讯云侧，其**出网请求不受该白名单限制**。
因此后端只要有**公网地址**（用 IP + HTTP 也可以）即可被访问，备案这一步可以完全省掉。
后端仍是现有 Java 服务，**一行都不用改**，云函数只做转发。

### 8.9 本地演示环境 vs 线上生产环境（Docker 只属于前者）

**一句话**：Docker 只是**开发与演示**用的本地运行方式，与小程序上线后的运行**没有任何关系**。
教职工手机里的小程序不会、也不需要跑 Docker。

**为什么要区分**

| 环境 | 用途 | 组成 | 谁来运行 |
| --- | --- | --- | --- |
| 本地演示（现在的 `docker-compose.yml`） | 开发、联调、验收演示 | MySQL + Redis + Java 后端 + Nginx，全在你电脑上 | 你的开发机 |
| 线上生产 | 真实发放期间对外服务 | 同一套 Java 后端 + MySQL（+ Redis），部署在一台**长期在线**的服务器/云上 | 服务器 |

关键点：**后端代码完全一样**，差别只在"跑在哪台机器上"以及 `.env` 里的地址与密码。
容器化（Docker）在这里的价值恰恰是——**同一份编排文件从本地搬到服务器即可**，不需要重装环境。

**上线时后端放哪儿（三条路，任选其一）**

| 方案 | 做法 | 备案要求 | 适用 |
| --- | --- | --- | --- |
| **A. 小程序原生页面 + 云函数转发**（当前已实现） | 后端部署在任意有**公网地址**的机器（云服务器 / 学校机房服务器，IP+HTTP 亦可），云函数转发请求 | **无需备案、无需 HTTPS 证书、无需配置服务器域名** | 首选。个人主体只能走这条 |
| **B. 微信云托管**（CloudBase Run） | 把现有的后端镜像直接部署到云托管，小程序用 `wx.cloud.callContainer` 调用 | **无需备案**（云托管通道不受 request 域名白名单约束） | 不想自己运维服务器时选它；与云开发同一套体系，按量付费 |
| **C. 传统自建服务器 + wx.request 直连** | 后端部署在云服务器，配 Nginx + HTTPS，小程序用 `wx.request` 直连 | **必须**：域名 ICP 备案 + HTTPS + 后台配置「服务器域名」 | 已有备案域名时才划算 |

> 当前 `miniprogram/config.js` 的 `useCloud` 开关就是为 A/B 两条免备案路线准备的；
> 只有选 C 时才需要把 `useCloud` 置 `false` 并配置服务器域名。

**搬家要做的事（从本地演示 → 线上）**

1. 服务器装 Docker（或直接装 JDK 17 + MySQL 8 + Nginx），把仓库拷上去
2. 改 `.env`：`MYSQL_ROOT_PASSWORD`、`ADMIN_INIT_PASSWORD` 换成强密码；接入真实短信时配 `SMS_PROVIDER=hbu` / `SMS_HBU_KEY`
3. 迁移数据：`mysqldump` 导出 → 服务器导入（若直接以 `db/init.sql` 起步，则只需导入甲方真实名单）
4. 起服务：`docker compose up -d`（首次启动会由 `DataInitializer` 建后台账号）
5. 小程序端：`miniprogram/README.md` 第四节，配 `cloudEnvId` + 云函数环境变量 `BACKEND_BASE_URL`
6. 逐条走一遍 §8.6 上线检查清单

**上线前务必关掉的演示开关**

| 项 | 位置 |
| --- | --- |
| 演示预填账号与提示 | `miniprogram/config.js` → `showDemoHint: false`；`miniapp/index.html` → `SHOW_DEMO_HINT = false` |
| 固定验证码 | `.env` → 清空 `MOCK_SMS_CODE`（真实通道下本已失效，清空避免混淆） |
| 短信自检接口 | `.env` → `SMS_TEST_ENABLED=false` |

**部署过程中遇到并解决的问题（都值得记下来）**

| # | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 1 | 服务器直连 `registry-1.docker.io` 返回 000，无法拉镜像 | 校园网到 Docker Hub 不通 | 配置 `registry-mirrors: https://docker.m.daocloud.io`（实测可达） |

| 4 | **MySQL 容器反复 unhealthy，日志报 `01-init.sql: Permission denied`** | 上传工具把文件权限设成了 **700**，而容器内以 `mysql` 用户（uid 999）读取挂载文件 | 改为 644 并重新执行（工具默认权限已修正） |
| 5 | SSH 执行 `docker exec` 类命令时整条链路卡死 | paramiko 未关闭 channel 的 stdin，`docker exec` 去读 stdin 就会一直阻塞 | `exec_command` 后显式 `stdin.close()`（工具已修正） |
| 6 | `tail /var/log/nginx/access.log` 看不到访问记录 | nginx 官方镜像把该文件软链到 `/dev/stdout` | 用 `docker logs hz-nginx` 查看 |

**公网可达性（已解决）**

服务器内网地址 `10.191.19.25`，已做端口映射到公网 **`http://221.192.236.175/`**。
经 5 个海外节点（加拿大 / 荷兰 / 斯洛文尼亚 / 乌克兰 / 美国）实测 **80 端口全部连通**，
接口契约检查在公网地址上跑同样 **44 / 44 通过**。

| 场景 | 能否访问 |
| --- | --- |
| 开发者工具模拟器 / 真机调试（勾「不校验合法域名」） | ✅ 可以（http + IP 即可） |
| 校内手机直接访问 H5 | ✅ 可以 |
| 校外手机浏览器访问 H5 | ✅ 可以 |
| 云函数侧转发 | ✅ 可以（云函数出网不受限） |
| **体验版 / 正式版小程序的 `wx.request`** | ❌ **不可以** —— 见下 |

**⚠️ 关键限制：`wx.request` 不接受「IP + http」**

微信对小程序的网络请求有硬性要求，**正式发布（体验版 / 正式版）时必须同时满足**：

1. 目标必须是 **HTTPS**（http 会被直接拒绝）
2. 必须是 **已 ICP 备案的域名**（**IP 地址不能作为合法域名**）
3. 该域名要在小程序后台「开发管理 → 开发设置 → 服务器域名」中登记

所以 `http://221.192.236.175` **只能用于开发调试**，不能直接用于正式版本。两条正式上线路径：

| 路径 | 做法 | 需要备案 | 需要 HTTPS 证书 |
| --- | --- | --- | --- |
| **① 云函数转发**（推荐，最省事） | 小程序原生页面 → `wx.cloud.callFunction` → 云函数 → `http://221.192.236.175/api`（云函数出网不受域名白名单约束） | ❌ 不需要 | ❌ 不需要 |
| ② 直连 | 申请域名 → ICP 备案 → 配 HTTPS 证书 → 登记服务器域名 → `wx.request` 直连 | ✅ 必须 | ✅ 必须 |

> 路径 ① 只需在 `miniprogram/config.js` 把 `useCloud` 改为 `true` 并填云环境 ID，
> 再部署云函数即可（后端地址已内置在云函数里兜底；想改地址时在控制台配环境变量
> `BACKEND_BASE_URL`，它优先于内置值）。
> 注意路径 ② 除了备案，还要考虑：**后台与登录接口目前在 http 上传输明文凭据**，
> 一旦对外正式使用，HTTPS 不只是微信的要求，也是必要的安全措施。

> **后台账号由应用启动时的 `DataInitializer` 创建**（仅在 `t_admin` 为空时执行）。
> 只导数据不重建容器 → `t_admin` 为空 → 后台登录直接失败。一键回归脚本已按此顺序编排。

该脚本会自动完成：导入 `db/init.sql` → 清空 Redis → **按 `.env` 重建后端容器**并等 `healthy` → 按序执行各套件 →
输出汇总表。**关键设计**：

- 每个套件分配互不相同的 C 端手机号（smoke 003/006、miniapp 008、fallback 009、carrier 010/011、loginguard 012），
  避免共用同一号码触发频控或失败锁定而误报；
- 后端容器用 `docker compose up -d --force-recreate api` 重建而非 `restart`——**环境变量只在容器创建时注入，
  `restart` 不会重新读取 `.env`**，改配置后必须重建；这同时也让上一次异常退出的容器配置自动回到 `.env` 声明状态；
- `test-sms-live.py` 会真实发短信并临时切换登录方式，因此**不参与默认回归**，只有显式传入 `HZ_SMS_PHONE` 才执行，

### 10.1 当前限制

| 项 | 说明 |
| --- | --- |
| 分页 | 后台页面一次性拉取最多 1000 条用于前端筛选与报表；订单量过万时需改为服务端分页 + 服务端聚合 |
| 轨迹查询 | 物流页通过批量接口一次取回轨迹（上限 500 单）。规模化后应在 `t_order` 冗余「最新轨迹」字段，避免回查轨迹表 |

| 物流轨迹 | 用户已可**按运单号自助查询**（§4.7）；但轨迹数据仍来自后台人工推进 / 运单号导入，尚未对接承运商开放接口或回调 |
| 承运商自选 | 用户可在启用承运商中自选，但**未做覆盖范围校验**（如某偏远地区该快递不到）。后台发货弹窗默认预选期望承运商，需人工确认可否履约 |
| 并发 | 库存与额度使用条件更新保证不超卖，但高并发下未做队列削峰 |
| 前端 | 原生单文件实现，未做组件化与按需加载；小程序为 web-view 壳，非原生页面 |
| 地址修改 | 未发货前可自助改 1 次；发货后彻底锁定（需联系客服）。改址不校验新地址与原地址的**跨省/跨区**差异，也未联动更新地址簿 |
| 售后申诉 | 发货后暂无异常上报入口（破损 / 未送达 / 未上门），只能走线下客服电话 |
| 库存预警 | `t_package.warn` 字段已预留阈值展示，但**未接入定时告警**，需人工查看套餐页 |
